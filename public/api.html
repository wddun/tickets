WTS Tickets API

Connect an event to anything that can make an HTTP request — a spreadsheet, a CRM, a Slack bot, a turnstile, your own website. Everything the dashboard does to registrations, this can do too.

Overview

The base URL is https://tickets.willstechsupport.com. Every endpoint lives under /api/v1, speaks JSON, and expects an API key.

A key belongs to exactly one event. No request names an event — the key decides which one, and nothing a caller sends can widen that. So a key you paste into a third-party tool can only ever touch the one event you made it for, and if it leaks, that is the whole blast radius.

Two ideas worth knowing before you start. A registration is one person and the tickets issued to them together — book three seats and that is one registration with three tickets, each with its own QR code. A scope is one permission, drawn from the same list used when sharing an event with a colleague.

Getting a key

  1. Open the event in the dashboard and go to Settings → API.
  2. Give the key a name describing what will use it — you will thank yourself later.
  3. Tick only the permissions that thing actually needs.
  4. Copy the key. It is shown once and never again — only a hash is stored, so it cannot be looked up later. Lost a key? Revoke it and make another.

Keys look like wts_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx. Treat one like a password: it is a bearer credential, so anyone holding it can do what it allows. Keep it server-side. Never put it in a web page, a mobile app, or a public repository.

A key is never stronger than the person who made it. Its permissions are re-checked against that account's current access on every request. If their access to the event is reduced, the key narrows to match; if it is removed, the key stops working. You cannot create a key that can do more than you can.

Authentication

Send the key as a bearer token:

curl https://tickets.willstechsupport.com/api/v1/me \
  -H "Authorization: Bearer wts_your_key_here"

If your tool can only set a plain header, X-API-Key: wts_your_key_here works identically. Start with /api/v1/me — it tells you which event the key is for and what it may do, and needs no scope.

Scopes

Each endpoint needs one scope. Give a key the fewest it can do its job with.

ScopeLets the key
checkinRead the event, its registrations and availability; check people in; scan tickets
undo_checkinReverse a check-in
manage_ticketsCreate, edit and delete registrations
email_attendeesSend a ticket by email when creating a registration
manage_waitlistRead the waitlist and promote from it
manage_paymentsRead orders
manage_eventRead the audit log
export_dataBulk export of attendee data

Sharing an event with other people is deliberately not available to a key. Granting someone access stays something a person does while signed in.

Errors

Every failure is a JSON object with a stable machine-readable code and a message meant for a human.

{
  "error": {
    "code": "missing_scope",
    "message": "This key does not have the \"manage_waitlist\" scope for this event."
  }
}
StatusCodeMeans
400invalid_requestSomething is missing or malformed. The message says what.
401missing_key / invalid_keyNo key sent, or it is unknown or revoked.
403missing_scopeThe key is valid but lacks the scope this endpoint needs.
404not_foundNo such thing on this event. Ids belonging to other events read as not found.
409sold_outThe event is full. Seats held by people mid-signup count as taken.
429rate_limitedSlow down — see below.

Rate limits

300 requests per minute per key. The limit is counted per key rather than per IP address, so one integration cannot exhaust another's budget. Responses carry the standard RateLimit-* headers; on a 429, wait and retry.

For a live counter, poll /api/v1/availability — it is the cheapest endpoint here. Once every few seconds is plenty; there is no need to poll harder than a human can read.

GET/api/v1/availabilitycheckin

Seat counts only — the endpoint to poll for a live "spots left" display.

{ "capacity": 250, "registered": 143, "held": 2, "remaining": 105, "soldOut": false, "unlimited": false }
held is people mid-signup. Someone with the registration form open holds their seat for a few minutes. Those seats are already spoken for, which is why remaining can be lower than capacity − registered.

GET/api/v1/registrations/:idcheckin

One registration, same shape as above.

POST/api/v1/registrationsmanage_tickets

Issue tickets. Returns 201 and the new registration.

curl -X POST https://tickets.willstechsupport.com/api/v1/registrations \
  -H "Authorization: Bearer wts_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{
        "name": "Ada Lovelace",
        "email": "ada@example.com",
        "ticketCount": 2,
        "customFields": { "Meal": "Vegetarian" },
        "sendEmail": true
      }'

sendEmail defaults to false, and needs the email_attendees scope to take effect. Importing a list of people who already have their tickets should not fire a surprise mailshot, so you have to ask for it.

If the event is full: 409 sold_out, or — when the waitlist is enabled — 202 with {"waitlisted": true, "position": 4}. Either way no ticket is issued, and a seat someone else is mid-signup for is never taken.

PATCH/api/v1/registrations/:idmanage_tickets

Change name, email or customFields. Applies to every ticket in the group. Omitted fields are left alone.

DELETE/api/v1/registrations/:idmanage_tickets

Removes the registration and all its tickets. Returns {"deleted": 2}.

Check-in & scanning

POST/api/v1/registrations/:id/checkincheckin

Marks everyone in the group as arrived. Safe to call twice — a repeat returns 200 with "alreadyCheckedIn": true rather than failing, so a retrying integration cannot get stuck.

DELETE/api/v1/registrations/:id/checkinundo_checkin

Reverses it.

POST/api/v1/scancheckin

The door, for your own hardware — a turnstile, a kiosk, a handheld reader. Send what the QR code contains (with or without the ticket: prefix) and get back the verdict the built-in scanner would show. 

curl -X POST https://tickets.willstechsupport.com/api/v1/scan \
  -H "Authorization: Bearer wts_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{"token": "ticket:N1m-PEIiE9aF"}'
statusMeans
validGenuine, unused — now checked in. Let them in.
already_usedReal ticket, already scanned. checkedInAt says when.
invalidNot a ticket for this event. A ticket from another event reads as invalid and reveals nothing about it.

Waitlist

GET/api/v1/waitlistmanage_waitlist

Everyone waiting, with their live position.

POST/api/v1/waitlist/:id/promotemanage_waitlist

Issues a free ticket and marks the entry converted. On a paid event this returns 409 paid_event: promoting there sends a personal checkout link, and money only ever changes hands through Stripe.

Orders

GET/api/v1/ordersmanage_payments

Paid orders for the event.

Paid ticketing is in beta and is a testing-only feature. Taking real money needs your own Stripe account connected to this system — email support@willstechsupport.com to get set up.

Audit log

GET/api/v1/audit-logmanage_event

Who did what to this event, newest first, paginated with limit and offset. Writes made through the API appear here too, attributed to the key by name — so you can always tell which integration did something.

Worked examples

Add someone from your own signup form

Scopes: manage_tickets, plus email_attendees to send them the ticket.

const res = await fetch('https://tickets.willstechsupport.com/api/v1/registrations', {
  method: 'POST',
  headers: {
    'Authorization': `Bearer ${process.env.WTS_KEY}`,
    'Content-Type': 'application/json',
  },
  body: JSON.stringify({ name, email, sendEmail: true }),
});

if (res.status === 202) {
  const { position } = await res.json();
  return `The event is full — you're number ${position} on the waitlist.`;
}
if (!res.ok) {
  const { error } = await res.json();
  throw new Error(error.message);   // written to be shown to a person
}

A live "spots left" counter on your website

Scope: checkin. Call this from your server, not the browser — the key must not be public.

const { remaining, soldOut } = await fetch(
  'https://tickets.willstechsupport.com/api/v1/availability',
  { headers: { Authorization: `Bearer ${process.env.WTS_KEY}` } },
).then(r => r.json());

document.querySelector('#spots').textContent =
  soldOut ? 'Sold out' : `${remaining} tickets left`;

Nightly export to a spreadsheet or warehouse

Scope: checkin. Page through in batches of 500.

let offset = 0, all = [];
for (;;) {
  const page = await fetch(
    `https://tickets.willstechsupport.com/api/v1/registrations?limit=500&offset=${offset}`,
    { headers: { Authorization: `Bearer ${KEY}` } },
  ).then(r => r.json());

  all.push(...page.registrations);
  offset += 500;
  if (offset >= page.total) break;
}

Post arrivals into Slack

Scope: checkin. Poll for new check-ins and forward them.

const arrived = await fetch(
  'https://tickets.willstechsupport.com/api/v1/registrations?checkedIn=true',
  { headers: { Authorization: `Bearer ${KEY}` } },
).then(r => r.json());

for (const r of arrived.registrations) {
  if (seen.has(r.id)) continue;
  seen.add(r.id);
  await postToSlack(`${r.name} just arrived (${r.ticketCount} ticket(s))`);
}

Getting help

Stuck, or want something the API doesn't do yet? Email support@willstechsupport.com — include the key's name and prefix (never the key itself) and what you were trying to do.
